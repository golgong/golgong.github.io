상품명만 보고 순금 목걸이를 가려내는 실험

공개 데이터 분석자료 수집·가공

상품명 102,059행의 누수 방지 평가를 다시 마치고, 같은 판정을 Python 없이 실행하는 C++ 프로그램까지 만들었습니다. 공식 API의 최초 108행 평가는 수집기 동결 기록이 빠져 엄격한 봉인 증거에서 제외했습니다. 선검증을 보완한 재수집에서는 새 카탈로그 7,148건을 확인했지만 새 순금 목걸이는 나오지 않았습니다.

이번 결과에는 서로 다른 세 가지 확인이 들어 있습니다. 기존 자료를 빠짐없이 나눈 평가, 그 결과를 그대로 옮긴 C++ 실행 파일, 모델을 고정한 뒤 받은 새 자료 평가입니다. 세 결과가 말해 주는 범위는 서로 다릅니다.

102,059행을 같은 기준으로 다시 평가했습니다

기준 자료는 상품명 102,059행입니다. 실제 순금 목걸이는 310행입니다. 같은 상품의 옵션이나 판매처만 다른 행이 학습과 시험 양쪽에 섞이지 않도록 묶은 뒤, 23차례로 나눠 평가했습니다. TP는 맞게 찾은 순금 목걸이, FP는 잘못 통과시킨 다른 상품, FN은 놓친 순금 목걸이입니다.

v12b는 v11보다 놓친 순금 목걸이를 7행 줄였습니다. 정밀도는 96.32%, 자동 확정 범위는 92.90%였습니다. 재질과 형태만으로는 골드바나 부품처럼 제목 일부가 비슷한 상품이 남았습니다.

그래서 상품명에 적힌 무게와 수량을 따로 읽는 mass-v3 규칙을 만들었습니다. 규칙과 시험 자료의 해시를 먼저 외부에 남긴 뒤 같은 입력으로 다시 계산했고, 57개 경계 사례도 고정했습니다. 결합 결과는 TP 288, FP 2, FN 22였습니다.

다만 이 수치는 소진된 진단 데이터의 결과입니다. 남은 오탐을 본 뒤 규칙을 만들었으므로 99.31%라는 결합 정밀도를 새 상품의 성능으로 광고할 수는 없습니다. 확인된 것은 어떤 오탐을 어떤 근거로 막았는지와, 고정된 규칙을 다시 실행하면 같은 결과가 나온다는 점입니다.

같은 판정을 C++ 단품으로 옮겼습니다

재질 모델과 형태 모델을 Windows용 C++ 실행 파일에서 직접 읽도록 옮겼습니다. 운영 모델 두 파일은 합계 약 3.73MiB이며 실행할 때 Python이 필요하지 않습니다. 한글과 영문이 섞인 상품명이 Python과 다르게 정리되지 않도록 Unicode 15 기준의 문자 정규화와 소문자 변환도 실행 파일 안에 넣었습니다.

Python과 C++의 판정 일치 검사는 재질 Top-1 1,200/1,200건, 형태 Top-1 400/400건이 같았습니다. 재질 Top-3 순서까지 비교하면 1,199/1,200건이 같았고, 한 건은 2위와 3위의 순서만 바뀌었습니다. 무게 규칙의 경계 사례 57건도 모두 일치했습니다.

이 결과는 모델을 가벼운 단독 프로그램으로 배포할 수 있다는 기술 확인입니다. C++에서 같은 답이 나온다는 사실이 새 상품에 대한 정확도를 보증하지는 않습니다.

공식 API의 새 자료 108행을 평가했습니다

다음에는 모델과 규칙을 바꾸지 않은 채 네이버 커머스 공식 API를 16개 검색어로 조회했습니다. 응답 372행에서 중복 상품과 기존 102,059행에 있던 상품을 제외하고, 처음 보는 카탈로그 108행만 남겼습니다.

문제는 이 108행 안에 공식 분류가 순금 목걸이인 상품이 한 건도 없었다는 점입니다. 따라서 새 순금 목걸이를 얼마나 찾았는지는 계산할 수 없었습니다. v12b는 골드바 문구가 들어간 14K 목걸이 한 건을 순금으로 잘못 통과시켰고, mass-v3를 결합하자 이 한 건은 자동 확정에서 빠졌습니다.

새 자료에서 v12b는 TP 0, FP 1, FN 0이었고, mass-v3를 결합한 결과는 TP 0, FP 0, FN 0이었습니다. 두 결과 모두 표적 상품이 없어 성능 판정에는 사용할 수 없습니다.

이번 새 자료 평가의 결과 판정은 inconclusive입니다. 정답 대상이 없는 표본으로는 통과와 실패 어느 쪽도 결정할 수 없다는 뜻입니다. 확인된 사실은 새 자료에서 오탐 하나를 막았다는 것뿐입니다.

독립 감사에서는 108행과 TP·FP·FN 수치를 모두 다시 계산해 같은 결과를 확인했습니다. 다만 사전 동결 계획에 실제 HTTP 요청과 응답 해석을 담당한 commerce_catalog_collector.py의 해시가 빠져 있었습니다. 데이터 수집기까지 처음부터 고정됐다는 증거가 부족하므로, 감사 결과는 REQUEST_CHANGES였고 이 결과를 엄격한 봉인 증거에서는 제외했습니다.

7,148개의 새 카탈로그까지 넓혔습니다

수집 코드를 불러온 뒤 파일을 확인하던 순서를 고쳤습니다. 새 v14r6은 Python을 격리 모드로 시작해 런타임 4,858개 파일, 제3자 패키지 영역 31,950개 파일, 로컬 수집 소스 123개, TLS 인증서와 기존 자료의 해시를 먼저 확인합니다. 수집 코드가 미리 불리지 않았는지도 검사합니다. 모두 맞아야 공식 API를 호출하며, 통과 영수증과 실행 기록은 수집 DB와 결과 파일에 함께 남습니다.

92개 검색어로 상품 모델 API 234페이지를 조회하고 분류표도 한 번 확인했습니다. 응답 17,122행을 합치면 고유 카탈로그 8,090개였고, 기존 자료와 겹친 942개를 제외하면 처음 보는 카탈로그는 7,148개였습니다. 기존 순금 목걸이는 310개 중 309개가 다시 나타났지만 공식 분류가 순금 목걸이인 새 상품은 0개였습니다.

새 자료에는 14K 목걸이 2,767개, 패션 목걸이 2,013개, 랩다이아몬드·모이사나이트 목걸이 578개, 18K 목걸이 543개가 들어 있었습니다. 결과 수 상한에 닿은 검색어 3개는 API가 알린 마지막 페이지까지 11페이지를 더 확인했습니다. 그래도 새 순금 목걸이는 나오지 않았습니다.

이 결과는 API 고장이 아닙니다. 상품 모델 API는 이름으로 카탈로그를 찾지만 특정 카테고리 전체를 차례로 내보내는 기능은 아닙니다. 검색어를 넓혀 인접 상품은 충분히 모았지만 새 표적 자료는 확보하지 못했습니다.

새 비표적 7,102개에서 오탐을 확인했습니다

바로 앞 시점인 v14r3에서 처음 본 상품 중 기존 자료와 겹치지 않고 공식 분류가 순금 목걸이가 아닌 7,102개를 따로 평가했습니다. 모델과 규칙은 바꾸지 않았습니다. 기본 v12b는 6개를 순금 목걸이로 잘못 자동 확정했고, 무게 근거를 확인하는 mass-v3를 결합하자 4개가 사람 확인 대상으로 돌아가 최종 오탐은 2개가 남았습니다.

남은 두 건의 공식 분류는 모두 패션 목걸이였습니다. 제목에는 금 거래소 브랜드와 g 단위 무게가 함께 적혀 있어 현재 규칙이 순금 근거로 읽었습니다. 이 두 건을 보고 다시 고친 모델을 같은 7,102건에 재평가하면 숫자를 부풀리게 되므로, 이번 자료에서는 오류로 그대로 남겼습니다.

C++ 실행 파일은 Python에서 기본 통과한 6개 전부와 고정 방식으로 뽑은 비통과 128개를 대조해 134/134가 일치했습니다. 이는 Windows 단품이 같은 판정을 실행한다는 확인입니다. 비표적만 있는 자료이므로 정밀도와 재현율은 계산할 수 없고, 0.0282%도 다른 상품 전체에 일반화할 성능 수치가 아닙니다.

결론은 실행기는 준비됐고 새 표적 자료가 부족합니다

상품명 분류 모델과 무게 규칙을 Python 없이 실행하는 C++ 단품 경로는 완성했습니다. 기존 누수 방지 평가에서는 실제 순금 목걸이의 92.90%를 자동 확정했고, 새 비표적 패널에서는 최종 오탐 2건을 확인했습니다.

그러나 공식 API 이름 검색에서 개발에 쓰이지 않은 새 순금 목걸이를 얻지 못했습니다. 따라서 무료 배포 제품의 재현율과 처음 보는 브랜드에서의 정확도를 아직 확정할 수 없습니다. 다음 모델은 이번 두 오탐을 학습용 hard negative로 사용할 수 있지만, 성능 판정은 이후 시점의 새 순금 목걸이와 혼동 상품을 함께 모은 별도 자료에서 해야 합니다.
